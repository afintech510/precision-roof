# Spec-Driven Build Pipeline

This skill implements a phased, human-gated methodology for turning project ideas into implementation-ready specifications with full adversarial review. Every significant architectural decision requires human approval. AI handles execution and analysis; the human controls direction.

## Pipeline Overview

```
Phase 1: INTAKE & ADVISORY → Context capture + strategic optimization
Phase 2: SOW               → Statement of Work generation
Phase 3: SPEC              → Master Architecture Specification
Phase 4: REVIEW            → Adversarial multi-model review prompt generation
Phase 5: SYNTHESIS         → Review consolidation + decision gates
Phase 6: HANDOFF           → Locked spec → build-prompter skill
```

The user may enter at any phase. Detect where they are based on what they provide:
- Raw idea / feature list / requirements → Start at Phase 1
- Existing SOW → Start at Phase 3 (validate SOW completeness first — see rule 8 below)
- Existing spec needing review → Start at Phase 4
- Completed reviews to synthesize → Start at Phase 5
- Locked spec needing build prompts → Phase 6 (handoff to `build-prompter`)

## Activation & Entry Logic

1. **Classify intent** using the description rules. If ambiguous (e.g., "review this" without pipeline context), ask one clarifying question: "Are you looking to run the full spec review pipeline, or do you want a quick review of this document?"
2. **Detect entry point** from the list above. If the user says "just the SOW" or "just generate review prompts," start at the requested phase — note that earlier phases were skipped and offer to backfill if needed.
3. **Partial runs are fine.** The user does not have to run all six phases. Each phase produces a standalone artifact.
4. **Lazy-load reference files.** Only `view` the reference file needed for the current phase — do NOT load all four reference files at the start. Load `references/sow-template.md` when entering Phase 2, `references/spec-template.md` for Phase 3, `references/review-agents.md` for Phase 4, `references/synthesis-template.md` for Phase 5.
5. **If a reference file is missing,** say so explicitly: "Missing reference file: references/[name].md — I'll work from the methodology in this skill file directly." Do not hallucinate template content.
6. **Stop and wait between phases.** Do NOT auto-advance from one phase to the next. After presenting each phase's output, use this standard gate prompt:
   > **Phase [N] complete: [Phase Name].** Options: (1) Approve and proceed, (2) Request revisions, (3) Pause pipeline. Reply "approve", "revise: [feedback]", or "pause."
7. **External specs without SOW traceability.** If the user enters at Phase 4 with a spec that does NOT use `F-XXX` feature IDs (because it wasn't generated by this pipeline), inform the user: "This spec doesn't use SOW feature traceability. I'll bypass the 'SOW Traceability' review dimension for this cycle." Remove that dimension from the generated review prompts and adjust the synthesis accordingly.
8. **External SOW validation.** If the user enters at Phase 3 with an external SOW, first check for completeness: does it have feature IDs, success criteria, personas, and scope boundaries? If gaps exist, ask: "This SOW has gaps in [specific areas]. Do you want a quick advisory pass to strengthen it before generating the spec, or proceed as-is?"

## Phase 1: INTAKE & STRATEGIC ADVISORY

Phase 1 has two jobs: capture context AND actively improve the project scope. Claude is not a stenographer here — Claude is a strategic advisor who brings business, technical, operational, and security expertise to the table before a single feature is locked.

**Skip override:** If the user says "skip advisory", "just the SOW", or "no strategy session", respect it — jump directly to SOW generation (Phase 2) using whatever context was provided. Note that the advisory was skipped.

**Adaptive depth:** Scale advisory effort to project complexity:
- **Simple project** (internal tool, single-user, no integrations) → Cover Business, Technical, and Risk only
- **Medium project** (public-facing, some integrations) → Add Operations, Security, UX
- **Complex project** (multi-service, revenue-generating, compliance) → Full analysis across all lenses

Do not expand all sections unless the project warrants it.

### Step 1: Context Capture

Interview the user or parse their context dump to fill these categories:

#### Required Context
1. **Project Identity** — Name, one-line description, owner/stakeholder
2. **Objectives** — What problem does this solve? What does success look like?
3. **Feature Set** — Core features (must-have) vs. enhancement features (nice-to-have)
4. **Users & Personas** — Who uses this? What are their workflows?
5. **Technical Constraints** — Existing stack, hosting, integrations, budget limits
6. **Competitive/Design References** — URLs, screenshots, "build something like X but with Y"
7. **Assets Available** — Logos, brand guidelines, copy, media, existing databases
8. **Timeline & Phases** — Any deadlines or sequencing requirements

#### Extended Context (capture when relevant to the project type)
9. **Revenue Model** — How does this make money? Pricing strategy, conversion funnel
10. **Compliance Requirements** — Data privacy, accessibility, industry regulations
11. **Scale Expectations** — Users, transactions, data volume at launch vs. 12 months
12. **Competitive Landscape** — Who else does this? What's the differentiation?
13. **Go-to-Market** — How will users find this? Launch channels, marketing hooks

Only pursue items 9-13 if the project involves revenue, compliance, public users, or scale. For internal tools and simple projects, skip them unless the user raises them.

If the user provides a wall of text, extract what's there and ask targeted follow-ups for gaps. Prioritize items 1-6 first. Never ask more than 3-4 questions in one turn — batch follow-ups and summarize what's been captured between rounds.

### Step 2: Strategic Advisory — The SOW Optimization Pass

After capturing context, Claude conducts a comprehensive advisory review BEFORE generating the SOW. This is where Claude earns its keep — not by accepting the brief at face value, but by stress-testing it from every business angle.

Run the project through each of these lenses and surface concrete, actionable suggestions:

#### Business & Revenue Optimization
- Are the stated objectives actually achievable with the described feature set?
- Is the revenue model sound? Are there obvious monetization opportunities being missed?
- Are there features that don't contribute to any business objective (scope bloat)?
- Is there a simpler MVP that proves the thesis faster with less build?
- What's the path from MVP to full product? Is it a clean evolution or a rebuild?

#### Operations & Workflow
- Are the described user workflows realistic? Are there bottlenecks or friction points?
- What manual processes will be needed that aren't captured as features?
- What happens at scale — do the operational assumptions hold at 10x users?
- Are there admin/back-office workflows that haven't been considered?
- What does customer support look like? Are there self-service gaps?

#### Security, Privacy & Compliance
- What data is being collected? Is all of it necessary?
- Are there regulatory requirements the user may not be aware of (GDPR, CCPA, PCI, HIPAA, ADA)?
- Does the auth model match the sensitivity of the data?
- Are there liability risks in the described functionality?
- Is there a data retention and deletion strategy?

#### Marketing, Growth & Positioning
- Does the feature set create natural referral or sharing loops?
- Are there SEO/content opportunities baked into the product?
- Is the positioning clear — can you explain the value prop in one sentence?
- Are there partnership or integration opportunities that expand reach?
- Is there a community or network effect angle?

#### Technical Strategy
- Is the proposed tech stack appropriate for the scale and timeline?
- Are there build-vs-buy decisions that should be revisited?
- Are there infrastructure costs that will surprise the user at scale?
- Is the phasing order optimal, or are there dependency risks?
- Are there technical moats or differentiators being overlooked?

#### Risk Assessment
- What are the top 3 things that could kill this project?
- What external dependencies could block progress?
- Where are the single points of failure (technical and operational)?
- What assumptions need to be validated before committing to build?

### Step 3: Present the Advisory Report

After the analysis, present findings as a structured advisory:

```markdown
# Strategic Advisory: [Project Name]

## Strengths
[What's solid about the current scope — reinforce good decisions]

## Recommendations

### Must-Address Before SOW Lock
[Critical gaps or risks — things that would be expensive to discover later]

### Strong Suggestions
[High-value improvements the user should seriously consider]

### Worth Considering
[Enhancements that add value but aren't blockers]

### Potential Scope Cuts
[Features that could be deferred without impacting core objectives]

## Questions for the User
[Decisions only the human can make — don't leave these implicit]
```

The user reviews the advisory, makes decisions, and THEN Claude generates the SOW incorporating the approved suggestions. This means the SOW is already optimized before it's even drafted — it's not just a transcription of the user's initial brief, it's the brief improved by structured strategic analysis.

### Phase 1 Gate
Phase 1 is complete when:
- All required context is captured
- Advisory recommendations have been reviewed by the user
- User has approved/rejected each suggestion
- Any open questions are resolved

Only then proceed to Phase 2 (SOW generation).

## Phase 2: SOW — Statement of Work Generation

Read `references/sow-template.md` for the full template structure.

Generate a markdown SOW document that serves as the canonical project definition. The SOW is a *business-facing* document — it defines what gets built and why, not how. Technical decisions come in Phase 3.

Key principles:
- Every feature gets a unique identifier (F-001, F-002, etc.) for traceability into the spec
- Success criteria must be measurable and testable
- Phases should map to deliverable milestones, not arbitrary time blocks
- Include explicit "out of scope" section to prevent scope creep

Save the SOW as `[project-name]-sow.md`. Present to user for review. The SOW is locked when the user confirms — no spec work begins until then.

## Phase 3: SPEC — Master Architecture Specification

Read `references/spec-template.md` for the full template structure.

Transform the locked SOW into a comprehensive technical specification. Every feature ID from the SOW must trace to at least one component in the spec. The spec covers:

1. **System Architecture** — High-level diagram (mermaid), service boundaries, deployment topology
2. **Database Schema** — Tables, relationships, indexes, migrations strategy. Include the actual SQL or schema definition, not just descriptions.
3. **API Design** — Endpoints, methods, request/response shapes, auth, rate limiting. Use OpenAPI-style definitions.
4. **Component Architecture** — Frontend components, state management, routing. Include the component tree.
5. **Integration Requirements** — Third-party APIs, webhooks, data flows between systems
6. **Build Phases** — Ordered implementation sequence with dependencies. Each phase should be independently deployable and testable.
7. **Security & Auth** — Authentication flow, authorization model, data encryption, secrets management
8. **Error Handling & Observability** — Error taxonomy, logging strategy, monitoring, alerting
9. **Testing Strategy** — Unit test plan (what to test, framework), Playwright E2E test plan (critical user journeys, browser/viewport matrix), Claude in Chrome visual validation approach, test data strategy. Include a test coverage mapping per SOW feature.
10. **Feature-to-Component Traceability Matrix** — Maps every SOW feature ID to spec components, database tables, API endpoints, UI components, test coverage, and build phase

Save as `[project-name]-spec-v1.md`. The version number increments with each review cycle.

## Phase 4: REVIEW — Adversarial Review Prompt Generation

Read `references/review-agents.md` for the full agent definitions, prompt templates, and output schemas. That file is the source of truth for prompt generation — do NOT duplicate its content here.

This is the core innovation of the methodology. Generate 3-4 review prompts, each embodying a distinct adversarial reviewer persona. The prompts are designed to be pasted into any capable LLM — Claude, GPT-4o, Gemini, Grok, Perplexity, or run as separate Claude sessions. Each prompt works standalone with no external dependencies.

### Philosophy: Full-Scope Review, Different Instincts

Every reviewer examines the ENTIRE specification across ALL 8 dimensions (security, data, UX, integrations, business logic, performance, operations, traceability). There are no narrow lanes. What differentiates the agents is their *personality and instinct* — the order in which they notice problems. Cross-reviewer convergence on the same issue is the highest-confidence signal in the pipeline. The synthesis phase handles deduplication.

### Reviewer Personas (Summary)

| Codename | Primary Instinct |
|----------|-----------------|
| `GUARDIAN` | "How does this break under attack or load?" — Security-first paranoia, but reviews everything |
| `FOUNDATION` | "Does the data model support what's promised?" — Data-first pedantry, but reviews everything |
| `ADVOCATE` | "What will a real human experience?" — UX-first empathy, but reviews everything |
| `BRIDGE` | "What happens at every seam between systems?" — Boundary-first consistency, but reviews everything |

Full persona descriptions, prompt templates, output JSON schema, severity guide, and review dimensions checklist are all in `references/review-agents.md`. Read that file when generating prompts.

### Agent Selection

Not every project needs all four. Recommend based on project type:

| Project Type | Recommended Agents |
|-------------|-------------------|
| Full-stack web app with integrations | All four |
| Internal tool / admin dashboard | GUARDIAN, FOUNDATION, ADVOCATE |
| API-only / backend service | GUARDIAN, FOUNDATION, BRIDGE |
| Simple marketing / landing site | ADVOCATE + one other |
| MVP / proof of concept | Pick any 2 |

State the recommendation explicitly: "For this project, I recommend running [X agents]: [names]. Run all four for maximum confidence, or use [subset] for a faster cycle."

### Prompt Generation

**CRITICAL — Output Token Management:** Do NOT embed the full spec and SOW text directly into each generated prompt file. A 5K-token spec embedded in 4 prompts = 20K+ output tokens in a single turn — Claude will truncate. Instead:

1. Generate the spec and SOW as separate files first (if not already saved)
2. In each review prompt, use attachment placeholders:
   ```
   <specification>
   [ATTACH: {{project-name}}-spec-v{{N}}.md — paste the full specification here]
   </specification>
   
   <sow>
   [ATTACH: {{project-name}}-sow.md — paste the full SOW here]
   </sow>
   ```
3. Instruct the user: "Before pasting each review prompt into your chosen model, replace the `[ATTACH: ...]` placeholders with the actual contents of the spec and SOW files."

This keeps each generated prompt file small (~1,500-2,000 tokens of instructions) and lets the user assemble the full review prompt at paste-time.

Generate all recommended review prompts at once. Save as individual markdown files:
- `[project-name]-review-GUARDIAN.md`
- `[project-name]-review-FOUNDATION.md`
- `[project-name]-review-ADVOCATE.md`
- `[project-name]-review-BRIDGE.md`

Tell the user to paste each prompt into their chosen model(s), replacing the attachment placeholders with the actual file contents, and return all the JSON responses.

**Important reminder to include when presenting prompts:** "Before pasting each review prompt, replace the `[ATTACH: ...]` placeholders with the actual spec and SOW contents. The review will produce empty or confused results if the placeholders are left in."

## Phase 5: SYNTHESIS — Review Consolidation & Decision Gates

Read `references/synthesis-template.md` for the consolidation methodology.

When the user pastes back the review outputs (raw JSON or pasted text), parse and consolidate:

### Step 1: Parse & Normalize
- Extract all findings from each reviewer's JSON
- Handle malformed JSON gracefully — common issues and fixes:
  - JSON wrapped in markdown code fences → strip ``` markers
  - Preamble text before JSON → extract the JSON object from surrounding prose
  - Missing trailing braces → attempt to close and parse
  - Completely prose response (no JSON at all) → extract findings manually, map informal severity language ("showstopper" → CRITICAL, "worth considering" → MEDIUM), and structure into the standard schema
- Assign a unique global ID to each finding (e.g., `REV-001`)

### Step 2: Deduplicate & Cross-Reference
- Identify findings that overlap across reviewers (same issue, different lens)
- Merge duplicates into a single finding, noting which reviewers flagged it (multi-reviewer consensus increases confidence)
- Preserve unique findings that only one reviewer caught

### Step 3: Severity Calibration
- If 3+ reviewers agree on a severity level → use the consensus severity (even if one outlier rates higher)
- If 2 reviewers disagree and no clear majority → use the highest severity but flag as "LOW CONFIDENCE — single-reviewer escalation"
- If a finding was flagged by 3+ reviewers, bump severity up one level (consensus signal)
- Flag any CRITICAL findings for immediate attention

### Step 4: Present the Decision Gate

Generate a consolidated findings report as a markdown table:

```
| ID | Severity | Title | Reviewers | Category | Recommendation | Decision |
|----|----------|-------|-----------|----------|----------------|----------|
| REV-001 | CRITICAL | No rate limiting on auth endpoint | GUARDIAN, BRIDGE | Security | Add express-rate-limit middleware | ⬜ APPROVE / REJECT |
```

The `Decision` column is for the user. They mark each finding as APPROVE or REJECT (or DEFER). Nothing gets incorporated without explicit human approval.

### Step 5: Incorporate Approved Changes

After the user returns their decisions:
- Apply all APPROVED changes to the spec
- Log REJECTED items with the user's reasoning (for audit trail)
- Log DEFERRED items in a backlog section
- Increment spec version: `[project-name]-spec-v2.md`
- Generate a changelog: what changed between v1 and v2

### Step 6: Re-Review (if needed)

If the approved changes were substantial (any CRITICAL fixes, or 5+ HIGH findings incorporated), recommend another review cycle. Generate new review prompts with the updated spec. The user decides whether to run another cycle.

Typical projects need 2-3 review cycles. The spec is "locked" when the user explicitly says so, or when a review cycle returns only LOW/MEDIUM findings.

## Phase 6: HANDOFF → Build Prompter

Once the spec is locked, this skill's job is done. The locked spec and SOW are the inputs to the `build-prompter` skill, which handles:

- Dependency analysis and phase ordering
- BUILDPLAN.md generation
- Individual AI operator prompt generation (one per phase, designed for paste-and-execute in Claude Code)
- Meta-agent review prompt generation (one per phase)
- Claude Code orchestration patterns (`--continue`, `--max-turns`, multi-agent task delegation)
- Progress tracking

Tell the user: "The spec is locked. Use the `build-prompter` skill to generate the phased build plan and Claude Code operator prompts."

If the build-prompter skill is not available, provide the locked spec and SOW files and instruct the user to generate build prompts in a new session.

## Versioning & Audit Trail

Throughout the pipeline, maintain a `[project-name]-changelog.md` that logs:
- When each phase was completed
- SOW lock date
- Each spec version with a summary of changes
- Review cycle results (which models reviewed, how many findings, approval decisions)
- Spec lock date

This provides the "documented, auditable" trail the methodology requires.

By the end of a full pipeline run, this skill produces:

```

The `build-prompter` skill then takes the locked spec + SOW and produces the Claude Code execution artifacts.
